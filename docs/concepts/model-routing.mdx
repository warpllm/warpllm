Every request names a model as `provider/model`. That string is the whole
routing decision: it picks the provider, its base URL, the environment variable
holding its key, and the name sent upstream.

```json
{ "model": "openai/gpt-5-nano" }
```

## The prefix is required

warpllm matches the **whole string** against its registry. A bare `gpt-5-nano`
does not resolve, and neither does a name the registry has never heard of.

<Warning>
  An unlisted model is an error, not a guess. warpllm will not forward an
  unknown name to some upstream default and let you discover the routing on
  your bill.
</Warning>

```python
client.chat_completions({"model": "gpt-5-nano", ...})
# warpllm.BadRequestError: invalid model string 'gpt-5-nano':
# no registered model spec
```

There is no wildcard either. A registry entry of `openai/*` would register a
model literally named `*`.

## Switching providers

Because the request shape does not change, moving between providers is a string
edit plus the key that provider needs.

<CodeGroup>

```python Python
# OpenAI — needs OPENAI_API_KEY
client.chat_completions({"model": "openai/gpt-5-nano", "messages": messages})

# DeepSeek — needs DEEPSEEK_API_KEY
client.chat_completions({"model": "deepseek/deepseek-v4-flash", "messages": messages})

# Anthropic via OpenRouter — needs OPENROUTER_API_KEY
client.chat_completions({"model": "openrouter/anthropic/claude-sonnet-4", "messages": messages})
```

```ts TypeScript
// OpenAI — needs OPENAI_API_KEY
await client.chatCompletions({ model: 'openai/gpt-5-nano', messages })

// DeepSeek — needs DEEPSEEK_API_KEY
await client.chatCompletions({ model: 'deepseek/deepseek-v4-flash', messages })

// Anthropic via OpenRouter — needs OPENROUTER_API_KEY
await client.chatCompletions({ model: 'openrouter/anthropic/claude-sonnet-4', messages })
```

</CodeGroup>

A model name may contain further slashes after the provider prefix —
`openrouter/anthropic/claude-sonnet-4` is the OpenRouter provider serving the
`anthropic/claude-sonnet-4` slug.

## Claude over Anthropic's own protocol

`anthropic/` models go to `api.anthropic.com` directly, and they are the first
on the roster reached over a protocol that is not chat completions. Nothing
changes in your code: you send the same request shape and read the same reply
shape, and warpllm translates both ways.

```python Python
# Claude direct — needs ANTHROPIC_API_KEY
client.chat_completions({"model": "anthropic/claude-opus-5", "messages": messages})

# The same model through OpenRouter — needs OPENROUTER_API_KEY
client.chat_completions({"model": "openrouter/anthropic/claude-sonnet-4", "messages": messages})
```

Both routes work. Direct is one hop fewer and bills through Anthropic; the
OpenRouter entry stays registered and unchanged.

Two differences from a chat-completions provider are worth knowing:

<AccordionGroup>
  <Accordion title="max_tokens is always sent" icon="ruler">
    Anthropic requires it and chat completions does not, so warpllm falls back
    to the model's published output ceiling when you name none. Your own value
    always wins. A model whose ceiling is undocumented and a request naming no
    `max_tokens` is refused rather than given an invented default — truncating
    a reply at a length nobody asked for looks like the model stopping early.
  </Accordion>
  <Accordion title="temperature, top_p and top_k are rejected by newer models" icon="triangle-exclamation">
    Anthropic deprecated all three on Claude Opus 4.7 and later: a non-default
    value returns a 400. warpllm forwards what you write rather than dropping
    it, because dropping a parameter would change your request instead of
    translating it — so the refusal is Anthropic's, with Anthropic's message.
    Omit them for those models and steer with the prompt.
  </Accordion>
  <Accordion title="Controls Anthropic cannot express are refused, not dropped" icon="ban">
    Everywhere else warpllm forwards what you write and lets the provider judge
    it. On a translated route the provider never receives the field, so it
    cannot judge it — and a silent drop would answer a different request than
    the one you sent. `n: 2` would come back as a single choice, which looks
    exactly like a model that ignored you.

    So these are refused with an `InvalidInput` error naming the field:

    | Field | Refused when |
    | --- | --- |
    | `n` | greater than 1 |
    | `frequency_penalty`, `presence_penalty` | non-zero |
    | `logprobs` | `true` |
    | `top_logprobs` | greater than 0 |
    | `logit_bias` | non-empty |
    | `seed` | any value |

    The value your SDK fills in when you asked for nothing — `n: 1`, zero
    penalties, `logprobs: false`, an empty bias map — is not refused, so an
    ordinary request carrying them still routes.

    `top_k` and `parallel_tool_calls` are NOT on this list: Anthropic has an
    equivalent for each, so warpllm translates them instead of refusing them.
  </Accordion>
  <Accordion title="Extended thinking cannot be combined with tool results" icon="brain">
    Anthropic requires the assistant turn holding a tool call to open with its
    own signed `thinking` block, and a chat-completions reply has nowhere to
    carry one — so the request that sends your tool results back cannot be
    built. warpllm refuses it with a `NotImplemented` error rather than letting
    Anthropic answer it with a 400.

    A single-turn tool call with thinking works, and so does
    thinking-without-tools; it is sending the results back that stops. Turn
    thinking off for a tool loop, or run the loop on a chat-completions
    provider. Tracked in
    [#23](https://github.com/warpllm/warpllm/issues/23).
  </Accordion>
</AccordionGroup>

## What the registry records

The registry lives at
[`crates/warpllm/src/registry/specs.yaml`](https://github.com/warpllm/warpllm/blob/main/crates/warpllm/src/registry/specs.yaml)
and is compiled into the binary. Each model entry carries:

<ResponseField name="supported_apis" type="list" required>
  Every surface the model serves. A model serves exactly what it lists — one it
  does not list is refused before a request goes out.
</ResponseField>

<ResponseField name="model" type="string">
  The name sent upstream. Defaults to the key's last segment; set explicitly
  when warpllm's alias differs from the provider's own name.
</ResponseField>

<ResponseField name="capabilities.max_input_tokens" type="integer">
  The provider's published context window, recorded verbatim.
</ResponseField>

<ResponseField name="capabilities.max_output_tokens" type="integer">
  The provider's published output ceiling, where one exists.
</ResponseField>

<ResponseField name="capabilities.max_concurrent_requests" type="integer">
  A documented per-model concurrency ceiling, where the provider publishes one.
</ResponseField>

<ResponseField name="deprecation_date" type="string">
  `YYYY-MM-DD`, the day the provider stops serving the model, when one has been
  announced. Nothing acts on it — an entry keeps resolving past its date.
</ResponseField>

<Note>
  Every optional field is genuinely optional, and an absent limit means the
  provider does not publish one — not that the limit is unlimited. warpllm
  omits a number rather than guessing it.
</Note>

## Reading capabilities at runtime

Rust callers can look a spec up directly, which is useful for sizing prompts
against the routed model's window.

```rust
use warpllm::fetch_model;

let (provider, spec) = fetch_model("openai/gpt-5-nano")?;

println!("{} sends this upstream as {}", provider.name(), spec.model());
if let Some(window) = spec.capabilities().max_input_tokens() {
    println!("context window: {window}");
}
```

`fetch_model` returns the provider spec and the model spec as a pair, or
[`Error::InvalidModel`](/concepts/errors) if the string does not resolve.

## Surfaces

A surface name is `<protocol>_<endpoint>`, which is how the registry records
the wire format a model speaks.

| Surface | Meaning | Status |
| --- | --- | --- |
| `openai_compat_chat_completions` | One request, one whole reply | Implemented |
| `openai_compat_chat_completions_stream` | The same, as server-sent events | Implemented |
| `openai_compat_responses` | OpenAI's Responses API | Not implemented |

## Spreading load, retrying, and failing over

A plain `Client` routes a request to exactly one model, and a failure comes
back to you to decide about. There is no retry loop and no fallback chain yet,
so the error taxonomy is what lets you write your own policy in the meantime —
see [Errors](/concepts/errors).

**Load balancing has landed on `main`** and is unreleased. `BalancedClient`
spreads requests across a weighted set of `provider/model` pairs using smooth
weighted round-robin, rewriting the request's `model` to the candidate it
picked — so the name you pass acts as a group, and each candidate is a concrete
route within it.

```rust
use warpllm::{BalancedClient, Client, ClientConfig};

let client = Client::new(ClientConfig::default())?;
let balanced = BalancedClient::new(&client, &[
    ("openai/gpt-5.6", 3),
    ("deepseek/deepseek-v4-pro", 1),
])?;
```

The candidate set is fixed at construction, and each selected candidate still
goes through the same admission checks a direct call does. It is Rust-only for
now — neither binding exposes it, and the gateway has no flag for it.

Failover is tracked in [issue #27](https://github.com/warpllm/warpllm/issues/27), load balancing in
[issue #28](https://github.com/warpllm/warpllm/issues/28).
